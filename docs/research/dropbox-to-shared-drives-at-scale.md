# Dropbox to Google Shared Drives at scale

This note records provider contracts and rclone **v1.75.0** behavior for the supplied 17-million-file / 120 TB migration scenario. It is fact-finding, not a migration design or a throughput measurement. No authenticated customer enumeration, download, upload, or purge was performed. **[INFERENCE]** labels derived consequences; **[UNVERIFIED]** identifies evidence gaps.

## 1. Dropbox namespaces, ownership and enumeration

**A team is not simply one member's root folder.** In the older team-folder configuration, team folders are mounted inside member homes. In the team-space configuration, member homes and accessible team folders sit below a root; depending on `has_team_shared_dropbox`, that root may be team-shared or member-specific. `/2/users/get_current_account` exposes `root_info.root_namespace_id` and `home_namespace_id`; these can differ. `/2/team/features/get_values` exposes `has_distinct_member_homes` and `has_team_shared_dropbox`. [Team files][team-files]

| Entity          | Identity and discovery                                                                                                                                                                                                                                                                                                                       |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Team space/root | The root namespace is distinct from a member's home in the team-space model. Default Full Dropbox calls are rooted to the member home; Path-Root is needed to see team-space content. [Team files][team-files]                                                                                                                               |
| Team folder     | Team-managed content, mounted in member homes in the older configuration. `team/team_folder/list` is a team-folder inventory, not an inventory of all member/shared content. For `has_team_shared_dropbox=true`, this endpoint returns information about the team space only. [Team files][team-files], [Team folder list][team-folder-list] |
| Member home     | A member-owned namespace; namespace metadata can identify its `team_member_id`. Home and app namespaces returned by team enumeration belong to the team or its members. [Namespaces list][namespaces]                                                                                                                                        |
| Shared folder   | A separate namespace with membership; it can be mounted at different paths and with different names in different member homes. Team-accessible shared folders may be owned by another user or team. [Team files][team-files], [Namespaces list][namespaces]                                                                                  |
| App folder      | Also included in team namespace enumeration; App Folder OAuth access is otherwise confined to the app's own folder and is not equivalent to Full Dropbox access. [Namespaces list][namespaces], [OAuth content access][oauth]                                                                                                                |

`/2/team/namespaces/list` and `/continue` enumerate team-accessible namespaces, including team folders, shared folders containing team members, home namespaces and app folders. The response has `namespace_id`, type, name, cursor and `has_more`; **duplicate namespaces may occur even across pages**. The endpoint's old `limit` argument is deprecated and has no effect. Dropbox documents combining this enumeration with Select-Admin and `files/list_folder` to enumerate team content. [Namespaces list][namespaces], [Team files][team-files]

**[INFERENCE] Duplicate-copy risk:** independently copying every member home with mounted folders included can copy one shared namespace multiple times. Deduplicating the namespace inventory by `namespace_id` identifies one namespace despite aliases; deduplicating by displayed path/name does not. This alone does not remove overlap between a separately enumerated namespace and its contents reached through a parent mount: `list_folder.include_mounted_folders` defaults to `true` and includes entries under app/shared/team-folder mounts. The API exposes the traversal boundary, but no specific deduplication implementation is prescribed here. [Team files][team-files], [Namespaces list][namespaces], [List folder][list-folder]

Namespace-relative paths such as `ns:1522576049/path/to/file` address the namespace independently of a member's mount location. File IDs survive moves/renames; revision IDs identify versions. **[INFERENCE]** These identities describe different things: one namespace ID is not one file ID, and team accessibility is not proof of team ownership. [File access identifiers][file-access], [Namespaces list][namespaces]

## 2. Team-wide read authorization and rclone identity options

### Scopes and consent

**Full Dropbox content access and read-only scopes are compatible.** Full Dropbox determines which existing content can be reached; scopes determine the allowed operations. A team administrator authorizes team scopes, producing a team-linked token rather than a token owned by that authorizing administrator. User scopes within that grant determine the User API calls allowed while acting as members. [OAuth][oauth], [Authentication types][auth]

| Scope                    | Documented use in this research                                                                                                                                                                                                                                      |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `team_data.member`       | Required for namespace enumeration and for either Select-User or Select-Admin with a team token; it does not replace each endpoint's own scope. [Namespaces list][namespaces], [Authentication types][auth]                                                          |
| `files.metadata.read`    | `files/list_folder` and `/continue`; legacy `paper/docs/list` also requires it. [List folder][list-folder], [Legacy Paper listing](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/paper/docs-list)                                             |
| `files.content.read`     | `files/download` and `files/export`. [Download][download], [Export][export]                                                                                                                                                                                          |
| `account_info.read`      | `users/get_current_account`, including root information; relevant to rclone root discovery. [Current account](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/users/get-current-account), [Pinned root discovery][rclone-root]                  |
| `team_info.read`         | Team feature discovery, including organization model and `upload_api_rate_limit`. [Team features](https://docs.dropboxapi.com/dropbox-api/api-reference/business-endpoints/team/features-get-values)                                                                 |
| `members.read`           | Team member listing/lookup; rclone email-based `impersonate` resolves the member through `MembersGetInfo`. [Members list](https://docs.dropboxapi.com/dropbox-api/api-reference/business-endpoints/team/members-list), [Pinned OAuth/identity code][rclone-identity] |
| `team_data.content.read` | `team/team_folder/list`; this is distinct from `team_data.member`. [Team folder list][team-folder-list]                                                                                                                                                              |
| `sharing.read`           | Shared-folder metadata/listing if using the Sharing API. [Shared folders](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/sharing/list-folders)                                                                                                 |
| `sharing.write`          | Mounting shared folders; this is a write permission, not required for the Files API namespace-reading path. [Mount folder][mount-folder], [Team files][team-files]                                                                                                   |

This is an endpoint-to-scope inventory, not a claim that every scope in the table is mandatory for every read workflow. **[INFERENCE]** A token granted only the necessary read scopes plus `team_data.member`, without content/metadata/sharing/administrative write scopes, is provider-enforced source-content read-only under the scoped API contract. That conclusion depends on the **actual grant**, not the program being named “copy,” an operator promise, or the breadth of the admin identity. Legacy “Team member file access” app permissions are broader and are not equivalent evidence of read-only access. No live token or app registration was inspected. [OAuth scope enforcement and legacy permissions][oauth], [Authentication types][auth]

### Headers and refresh tokens

- `Dropbox-API-Select-User: dbmid:...` acts as one member with that member's access. `Dropbox-API-Select-Admin: dbmid:...` acts as a team administrator. Read endpoints can support **Whole Team** mode, covering team folders/spaces and member homes; mutable endpoints may instead support **Team Admin** mode, excluding member homes. Not every User API endpoint supports Select-Admin. `list_folder`, `download` and `export` explicitly support Whole Team mode. [Authentication types][auth], [List folder][list-folder], [Download][download], [Export][export]
- `Dropbox-API-Path-Root` changes the namespace relative to which paths and returned paths are interpreted; it does not grant additional access. Supported modes include `home`, `root` and `namespace_id`. Without it, a Full Dropbox app normally starts in the selected member's home rather than the team space. [Team files][team-files], [List-folder header contract][list-folder]
- Offline access uses authorization-code OAuth with `token_access_type=offline`, returning a refresh token and short-lived access token. Refreshing uses `/oauth2/token` with `grant_type=refresh_token`. The documented `scope` parameter on refresh can request a subset of the originally granted scopes, not expand them. [OAuth refresh flow][oauth], [Token endpoint][authorization]

### Can the granted scopes be observed?

**Yes at token issuance; not established for arbitrary existing bearer tokens.** The authorization-code token response includes `scope`, defined as the permission set applied to the token. A refresh response includes `scope` **only when a `scope` request parameter was supplied**. Access tokens are opaque and must not be decoded as a scope proof. `include_granted_scopes=team` during authorization can include previously granted team scopes, so requested scopes alone need not describe the entire resulting grant. [Authorization contract][authorization]

**[UNVERIFIED]** No general token-introspection endpoint returning all scopes for an arbitrary bearer token was found in the current endpoint index. `/check/user` is an authenticated echo, not a scope inventory; the team linked-app listing exposes app identity and link metadata but not token scope sets. **[INFERENCE]** A successful read proves that read is allowed, not that writes are forbidden; a token response reporting the complete grant is stronger evidence than probing one endpoint. [API index][api-index], [Check user](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/check/user), [Linked-app metadata](https://docs.dropboxapi.com/dropbox-api/api-reference/business-endpoints/team/linked-apps-list-member-linked-apps)

### Exact rclone v1.75.0 options

| Option              | Pinned behavior                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `impersonate`       | Takes a **member email address**. Resolves it with `team.MembersGetInfo`, then sets the SDK member ID/Select-User context. OAuth setup adds `team_data.member` and `members.read`; help requires a custom app, configuring impersonation before OAuth, and team-admin approval. [Identity code][rclone-identity]                                                                                             |
| `impersonate_admin` | Takes the admin's **team-member ID**, not email; sets the Select-Admin context. OAuth adds `team_data.member`; custom-app/admin-approval requirements apply. [Option registration](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L223-L243), [Initialization][rclone-identity]                                                                                                    |
| `root_namespace`    | Explicit namespace ID overrides automatic root discovery. The backend emits Path-Root in `namespace_id` mode. Otherwise a leading slash triggers current-account root discovery: documented `remote:`/`remote:path` address personal content, while `remote:/` addresses the root containing team folders and the user folder. [Root/header code][rclone-root], [Business documentation][rclone-dropbox-doc] |
| `shared_folders`    | Empty root lists shared folders. A nonempty root resolves and **mounts** a shared folder, switches back to ordinary filesystem handling, and does not unmount afterward. This is not a namespace-deduplication flag and not a guaranteed read-only mode. [Pinned mount code][rclone-mount]                                                                                                                   |

**[INFERENCE]** A strictly read-only grant can deny rclone's `shared_folders` mount operation because Dropbox requires `sharing.write`; enabling that permission changes the read-only claim. Source readability and source mount-state mutation are separate concerns. [Mount endpoint][mount-folder], [Pinned mount code][rclone-mount]

## 3. Dropbox request limits and data transport accounting

**Do not conflate ordinary request throttling, namespace write contention and monthly data transport limits.** Dropbox describes them separately. [Performance][performance], [Transport limit][transport]

| Limit                  | Scope, response and evidence                                                                                                                                                                                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ordinary API requests  | Per authorization. User-linked apps: per linked user/app. Team-linked Business endpoints: per team. Team-linked User endpoints using Select-User: per member. Exact numerical quotas are not published. [Performance][performance]                                                  |
| Request throttling     | HTTP 429 with `too_many_requests` and `Retry-After` in seconds; throttled calls themselves count, so immediate retry loops consume more quota. [Performance][performance]                                                                                                           |
| Write contention       | HTTP 429 `too_many_write_operations` can result from namespace-lock contention caused by this app or other writers. Dropbox describes a `Retry-After` of zero for this case. It is not evidence of a source-download cap. [Performance][performance]                                |
| Monthly data transport | Applies per team across apps on affected plans; exhaustion is HTTP **403** `invalid_account_type/feature`, not the ordinary 429. Resets on the **first day of each month**. `team/features/get_values` → `upload_api_rate_limit` checks applicability. [Transport limit][transport] |

The current team-deployment page names **Standard, Advanced and Enterprise** with **1 billion upload operations/month**. The API transport page more generally says “certain Dropbox Business plans”; actual entitlement for this tenant is **[UNVERIFIED]** until its feature/account configuration is inspected. The older 25,000-call figure is not the current limit stated by the reviewed deployment page. [Deployment limits][deployments], [Transport limit][transport]

The transport documentation says counted endpoints are explicitly annotated. The reviewed annotations include `files/upload`, `files/upload_session/start`, `files/upload_session/append_v2` and `files/upload_session/append_batch`. These are **call counts**, not byte counts; small upload chunks consume more calls. The reviewed `download`, `export`, `list_folder` and `/continue` references have no such annotation, and the performance guide describes the transport restriction as an **upload-call** limit. Thus these source reads are not documented transport-limit consumers, while remaining subject to ordinary API throttling. This is not an assertion that every endpoint containing “upload” is charged identically. [Transport accounting][transport], [Upload](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/upload), [Session start][upload-session], [Append](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/upload-session-append-v-2), [Batch append](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/upload-session-append-batch), [Download][download], [Export][export], [Listing][list-folder], [Continue][list-continue]

**[UNVERIFIED]** The performance guide does not specify whether Select-Admin read traffic receives the same per-member treatment it explicitly assigns to Select-User, nor a guaranteed aggregate team download throughput. Shared-link bandwidth limits are a separate product surface, not an established quota for authenticated `files/download`. [Performance][performance], [Deployment shared-link limits][deployments]

rclone v1.75.0 retries typed rate-limit errors, respects positive retry-after values through its pacer, and also recognizes `too_many_requests`/`too_many_write_operations` strings. Its default minimum pacing delay is 10 ms; that is a client setting, not a promise of 100 requests/s from Dropbox. Restricted-content downloads are made non-retryable. [Pinned retry handling](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L450-L503), [Pacer constants](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L63-L68), [Restricted downloads](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L2016-L2023)

## 4. Counts, sizes, cursors and enumeration cost

**No public arbitrary-folder aggregate item-count or recursive-byte-total endpoint was found.** Folder metadata has identity/path/sharing information, but not a recursive item count or total byte size. `users/get_space_usage` reports account usage, not totals for a chosen mapping root. The reviewed Files API provides listing rather than a folder-count operation. This is a bounded documentation finding, not proof that Dropbox has no internal aggregate counters. [List-folder metadata][list-folder], [Space usage](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/users/get-space-usage), [API index][api-index]

Dropbox's `files/list_folder` can recurse with `recursive=true`. Its `limit` accepts **1–2,000**, is approximate, and can return slightly more entries; the numeric constraint was observed in the official page's HTML/schema because its Markdown representation omits that constraint. Follow the returned cursor while `has_more=true`; subsequent `list_folder/continue` calls can also obtain changes. A cursor can be invalidated with `reset`, requiring a new listing. The listing contract specifies ordered reconciliation of file/folder/deleted entries; raw response-entry counts are not automatically a deduplicated live inventory. [List folder][list-folder], [Continue/reset][list-continue]

The API warns that very large recursive trees can cause performance problems or errors and describes non-recursive traversal as a workaround. It also warns against concurrent list/continue calls with the same parameters for the same app/user. A successful initial response is therefore not evidence that all 17M entries have been enumerated. [List folder][list-folder]

**rclone v1.75.0 deliberately does not implement Dropbox backend `ListR`.** Its source explains that Dropbox's inconsistent ancestor casing in `path_display` motivates directory-by-directory traversal. Its `ListP` means **paginated listing**, sets `Recursive=false` and `Limit=1000`, and continues each directory's cursor. There is no registered Dropbox `list_chunk` option. `size` and `lsjson -R` use the generic recursive walker, which falls back to directory traversal when the backend lacks `ListR`; `--fast-list` cannot manufacture that missing implementation. The recursive cursor in change-notification code is not the command listing path. [Backend rationale][rclone-list-rationale], [List/ListP][rclone-list], [Options](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L173-L386), [Generic walker](https://github.com/rclone/rclone/blob/v1.75.0/fs/walk/walk.go#L65-L182), [Size command](https://github.com/rclone/rclone/blob/v1.75.0/cmd/size/size.go), [JSON listing](https://github.com/rclone/rclone/blob/v1.75.0/fs/operations/lsjson.go#L245-L273)

**[INFERENCE] Cost arithmetic, not a timing estimate:** 17,000,000 entries at 2,000 entries/page is approximately **8,500 pages** in an ideal packed recursive API traversal; at rclone's 1,000 setting, approximately **17,000 full-page equivalents**. Actual rclone calls also reflect one listing per visited folder, partial/empty pages, folders in addition to files, duplicate mounts, retries and changes. A folder-by-folder model is roughly the sum of each folder's required pages, with at least one request for an empty folder—not simply `17M / 1000`. Repeated sizing/listing/verification repeats metadata work unless a caller separately reuses results. No measured API latency, scan duration, output size or memory footprint for this tenant is available. [Listing contract][list-folder], [Pinned listing implementation][rclone-list]

`rclone size` counts visible **files**, not the Shared Drive total-item population including folders. Its counting code tracks objects whose size is negative as sizeless and does not add their unknown byte size. **[INFERENCE]** Hidden exports can be absent from the count and visible export objects can leave the byte total incomplete; an ordinary `size` result is not automatically a capacity count or an exact export-byte total. [Pinned Count](https://github.com/rclone/rclone/blob/v1.75.0/fs/operations/operations.go#L1024-L1039), [Export metadata][rclone-export-metadata], [Google item accounting][drive-structure]

[File access][file-access], [Download][download]                                                                                                                                                                                                                                                                                           |

[Paper migration][paper], [Export][export]                                                                                                                                                                                                                                                                                        |

[Paper migration][paper]                                                                                                                                                        |

rclone v1.75.0's Dropbox implementation enumerates through Files API `ListFolder`/`ListFolderContinue` and downloads exports through `Export`; it does not implement legacy Paper enumeration. **[INFERENCE]** Its documented Paper support cannot establish coverage of legacy documents outside the Dropbox filesystem. [Backend clients/listing][rclone-list], [Export implementation][rclone-export-open], [Dropbox Paper migration][paper]

### Pinned export behavior

- `export_formats` defaults to **`html,md`**. This backend recognizes only Dropbox API `html` → `.html` and `markdown` → `.md`; unsupported configured extensions fail initialization. It is not a general Office/PDF export-format registry. [Known formats](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L146-L154), [Export options][rclone-exports]
- Format selection filters `export_as`/`export_options` to recognized formats, prefers the configured extension order, and otherwise uses the first recognized available format. With no recognized format, the object is hidden by default. [Format selection](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L1773-L1804)
- `skip_exports=true` hides non-downloadable objects and takes precedence over `show_all_exports`. `show_all_exports=true` makes export objects listable with original names, but marks them list-only: attempting export/download returns `fs.ErrorObjectNotFound`. The option is described for server-side copying, not cross-provider downloading. [Export metadata][rclone-export-metadata], [Export open][rclone-export-open]
- Normal export objects initially have **size `-1` and an empty hash**. A trailing `.paper` is removed before the chosen extension is appended (`note.paper` → `note.html`); `.papert` is not stripped. Export response metadata supplies size/hash after opening the export. **[INFERENCE]** Listing-path and size comparisons must not mistake the original cloud object and an exported representation for identical representations. [Export metadata][rclone-export-metadata], [Export open][rclone-export-open], [Tagged documentation][rclone-dropbox-doc]
- There is no dedicated `.web` target-resolution path in the backend. **[INFERENCE]** A downloadable `.web` follows normal file handling; a non-downloadable one follows the generic export rules. Actual API metadata and downloadable representation for this tenant's shortcut/cloud-document population are **[UNVERIFIED]**. [Metadata dispatch](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L1889-L1899), [Google shortcut model][web-shortcuts]

rclone's Dropbox limitations also describe upload-rejected names such as `thumbs.db`. That is a **Dropbox destination/upload** restriction, not evidence that the same filenames should be omitted from a Dropbox-to-Drive read. Its documented restricted-content download error is a separate refusal. [Pinned limitations][rclone-dropbox-doc]

## 6. Hash semantics and cross-provider verification

**Dropbox `content_hash` is not ordinary whole-file SHA-256.** Split bytes into 4,194,304-byte blocks, SHA-256 each block, concatenate the **binary digests**, then SHA-256 that concatenation and encode in hexadecimal. An empty file has no blocks, so the final hash is SHA-256 of the empty string. [Dropbox hash definition][content-hash]

Google Drive's output-only `md5Checksum` applies to binary content stored in Drive. `sha1Checksum` and `sha256Checksum` are populated **if available**, only for content stored in Drive, not Docs Editors or shortcuts. The schema does not guarantee every existing binary has all three fields. [Drive File resource][drive-files]

rclone v1.75.0 declares Dropbox's hash set as only `DropboxHash`, while Drive declares MD5, SHA-1 and SHA-256. Its common-hash selection returns `hash.None` when the sets do not intersect; its `--checksum` equality path explicitly falls back to size-only. This is not an algorithm conversion or a successful content-hash comparison. [Dropbox hash declaration](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L1761-L1764), [Drive hashes](https://github.com/rclone/rclone/blob/v1.75.0/backend/drive/drive.go#L3388-L3391), [Comparison/fallback][rclone-comparison]

**[INFERENCE]** Ordinary copy comparison, transport success and independent content verification are different evidence. Native hash metadata cannot establish Dropbox-to-Drive equality by comparing the displayed 64-character hashes: one is a block-composite hash and the other may be whole-file SHA-256. Comparing the same algorithm requires obtaining the corresponding digest of actual source/export bytes (or of downloaded content on both sides); path/size equality alone does not establish byte equality. These are consequences of the provider algorithms, not a change to ADR-0014's selected verification policy. [Dropbox algorithm][content-hash], [Drive checksum fields][drive-files], [ADR-0014](../adr/0014-map-approval-and-listing-verification.md)

## 7. Names, paths, depth and file sizes

**Dropbox is case-insensitive; Drive paths are not unique identities.** rclone documents that Dropbox cannot contain both `Hello.doc` and `hello.doc` at the same location. Google Drive's File resource permits duplicate names within a folder and identifies parents by ID. **[INFERENCE]** Namespace/mapping overlap and duplicate destination names remain possible even without a case-only collision in the source. [Tagged Dropbox limitations][rclone-dropbox-doc], [Drive File resource][drive-files]

Dropbox's current naming article recommends full paths under **260 characters** for cross-platform operation, bans slash/backslash and describes additional Windows-sensitive characters. This is not evidence that every API-stored Dropbox path must satisfy a Windows local-path ceiling. rclone v1.75.0 contains `maxFileNameLength=255`; that implementation constant is not by itself a complete provider guarantee about Unicode byte/character accounting or total path length. **[UNVERIFIED]** A universal Dropbox API 2,000-character full-path limit, a definitive API per-name counting rule, and a universal Google Drive API filename/full-path character ceiling were not established by the reviewed allowed sources. [Dropbox naming guidance][names], [Pinned constant](https://github.com/rclone/rclone/blob/v1.75.0/backend/dropbox/dropbox.go#L94-L96), [Drive name/parent schema][drive-files]

rclone's Drive documentation says invalid UTF-8 bytes are replaced because JSON cannot represent them; Drive permits names containing `/` and names `.`/`..`. This is rclone's documented naming behavior, not proof of unlimited path/name length or identical behavior in desktop sync clients. [rclone Drive naming](https://rclone.org/drive/#restricted-filename-characters)

Shared Drives permit **100 folder levels**. Google's precise API wording is that a child folder cannot be stored under a folder more than 99 levels deep; the restriction applies to child folders. Exceeding it returns HTTP 403 `teamDriveHierarchyTooDeep`. **[INFERENCE]** Additional destination wrapper folders consume levels even if source paths themselves are valid. [Folder-depth contract][drive-structure], [Depth error][drive-errors]

## 8. Google item capacity, sustained writes, query quotas and trash

### Capacity and exact error reasons

**500,000 is a total item cap per Shared Drive**, including files, folders, shortcuts and items in trash. Permanently deleted items do not count. The cap error is HTTP **403**, reason **`teamDriveFileLimitExceeded`**, message “The file limit for this shared drive has been exceeded.” The dedicated shared-drive guides establish whole-drive scope despite confusing folder-oriented wording in part of the error guide. [User limits][drive-user-limits], [API structure limits][drive-structure], [Error contract][drive-errors]

**[INFERENCE]** `ceil(17,000,000 / 500,000) = 34` drives is only a mathematical lower bound for the stated **files alone**. Exactly 34 completely full drives leave no space for folders, shortcuts or trash; actual necessary capacity depends on those additional items and distribution. Neither 120 TB nor a count of only ordinary downloadable rclone objects determines the number of item slots consumed. [Google item accounting][drive-structure], [rclone export filtering][rclone-export-metadata]

### Documented sustained writes are not merely a community estimate

Google's official large-migration guidance explicitly says: **“avoid exceeding 3 requests per second of sustained write or insert requests, per account”**, and **“This rate limit can't be increased.”** The cited `support.google.com` article redirects to Google's Workspace Knowledge site. This is a documented sustained **request** rate, not a guarantee of three completed files per second, and not a general 3-RPS cap on reads. **[UNVERIFIED]** The guide does not define the exact enforcement window, burst allowance or calls-per-file accounting. [Google migration guidance][google-migration]

**[INFERENCE]** At one write per file and exactly 3 sustained writes/s, 17M files represent about **65.6 account-days** of writes before folder creation, extra writes, retries or byte transfer. That is arithmetic under explicit assumptions, not an operational completion estimate; the daily byte allowance and other bottlenecks remain separate. [Sustained-write guidance][google-migration], [Daily allowance][drive-limits]

### Request quotas: current units and a documentation discrepancy

The dedicated Drive API quota page currently lists **1,000,000 quota units/minute/project** and **325,000 quota units/minute/user/project**, and says project quotas can differ. Costs differ by method: examples include `files.get` **5 units**, `files.list` **100**, and `files.update` **50**. Additional backend rate checks can still return 429. These are not interchangeable with a fixed number of file creations per minute. [Current Drive quotas][drive-limits]

The large-migration article still quotes **20,000 calls per 100 seconds per user/project** for reads and writes. That conflicts with the dedicated quota page's current unit-based model. This note records the discrepancy rather than presenting both as one consistent current request quota. **[INFERENCE]** A higher unit quota does not establish that the separately documented 3 sustained writes/s/account guidance disappears. The companion acting-account research covers the quota transition and shared-project attribution; actual project quota configuration remains **[UNVERIFIED]** here. [Migration guide][google-migration], [Quota guide][drive-limits]

### Purging trash can reclaim capacity

Trashing an item does **not** free its item slot; permanent deletion does. Shared-drive trash is automatically permanently deleted after 30 days, and a Manager can permanently delete earlier. These are documented capabilities, not authorization to delete this customer's content. [Shared-drive item accounting][drive-structure], [Shared-drive deletion lifecycle](https://support.google.com/a/users/answer/9310154?hl=en)

Drive API v3 `files.emptyTrash` accepts `driveId` for a Shared Drive:

```text
DELETE https://www.googleapis.com/drive/v3/files/trash?driveId=SHARED_DRIVE_ID
```

The endpoint requires the `https://www.googleapis.com/auth/drive` OAuth scope; Google's deletion-permissions table allows emptying trash for `organizer`, not `fileOrganizer`/`writer`. Individual `files.delete` permanently deletes an item; for a Shared Drive it requires `organizer` on the parent and supports `supportsAllDrives=true`. **[UNVERIFIED]** No precise item-cap-counter refresh SLA was found, and the deletion guide cautions that bulk changes can take time to become visible. No purge was run. [Empty-trash API](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/emptyTrash), [Deletion/permissions](https://developers.google.com/workspace/drive/api/guides/delete), [Individual delete](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/delete)
