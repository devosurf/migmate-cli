> Context: wayfinding on [Decide live-only progress, replay semantics and historical event compaction](https://github.com/devosurf/migmate-cli/issues/88). Research date: 2026-10-20. Primary Google and rclone documentation only; repository unchanged. `[INFERENCE]` identifies conclusions/calculations rather than explicit vendor promises; `[UNVERIFIED]` identifies a point not established by the reviewed primary sources. The proposed deployment uses one service account, Drive-only domain-wide delegation (DWD), one Workspace subject per Migmate/rclone job, and domain-only Shared Drives.

## Five-line bottom line

1. **Technically credible, not a throughput promise:** one DWD service account can spread writes across 20 Workspace subjects; nominal **20 × 750 GB = 15 TB/day** is a ceiling calculation, not measured capacity. [DWD](https://developers.google.com/identity/protocols/oauth2/service-account#delegatingauthority), [limits](https://developers.google.com/workspace/drive/api/guides/limits)
2. **Not inherently forbidden:** Google recommends multi-user DWD migration and temporary sharding users; get written clearance for this exact third-party, migration-only-account design because anti-circumvention and business-function-account wording remains. [migration guidance](https://knowledge.workspace.google.com/admin/getting-started/google-drive-large-migration-best-practices), [sharding](https://support.google.com/workspacemigrate/answer/9326912?hl=en), [AUP](https://workspace.google.com/intl/en/terms/use_policy/)
3. **Next Google-side throughput constraint is metadata/request work**, governed by the shared project's actual quota, per-user/backend throttles and rclone pacing; twenty users do not create twenty project quotas. [current API model](https://developers.google.com/workspace/drive/api/guides/limits), [rclone pacing](https://rclone.org/drive/#drive-pacer-min-sleep)
4. **Capacity and partitioning are independent gates:** keep sufficient permanent pooled storage and more than the 34–50 files-only minimum shared drives once folders, trash and growth are counted. [storage](https://knowledge.workspace.google.com/admin/storage/google-workspace-storage-faq-for-admins), [item limits](https://support.google.com/a/users/answer/7338880?hl=en)
5. **Deletion is safe for shared-drive ownership, not guaranteed attribution or savings:** retain permanent managers; Flexible seats can stop billing, Annual commitments cannot; deleted-actor attribution can be lost. [deletion](https://knowledge.workspace.google.com/admin/users/delete-or-remove-a-user-from-your-organization), [billing](https://knowledge.workspace.google.com/admin/billing/compare-flexible-and-annual-fixed-term-payment-plans), [deleted actors](https://developers.google.com/workspace/drive/activity/v2/reference/rest/v2/activity/user)

## 1. Daily upload limit: what Google actually promises

### Exact wording and accounting scope

Google's Drive API limits page says:

> “Google Workspace users can only upload 750 GB per day between My Drive and all shared drives; this limit also applies to copies.”
>
> “Users who reach the 750 GB limit or upload a file larger than 750 GB can't upload or copy additional files until 24 hours have passed.”
>
> “The maximum file size that users can upload is 5 TB; only the first file that breaks the limit completes uploading. The maximum file size that users can copy is 750 GB.”

Source: [Drive API usage limits](https://developers.google.com/workspace/drive/api/guides/limits).

The user-facing shared-drive guide says **“Each user can upload and copy 750 GB to Drive within 24 hours”**, and **“The limit refreshes within 24 hours.”** Do not assume a midnight reset, a separately replenished allowance for each shared drive, or that a final oversized file turns 750 GB into a reliable higher daily rate. [Shared-drive upload/copy limits](https://support.google.com/a/users/answer/7338880?hl=en#uploads)

**DWD accounting:** OAuth documentation explicitly says the application can make API calls **as users** and explicitly selects the impersonated user. Google's large-migration guide specifically recommends distributing write activity over many impersonated users to avoid quota issues. **[INFERENCE]** Therefore treat each `subject` as the upload actor: all concurrent jobs impersonating `files@eidra.com` share that user's allowance; changing the service-account key while retaining that subject does not provide another user's allowance. **[UNVERIFIED]** The reviewed primary sources do not explicitly specify the backend debit algorithm for the 750-GB counter under DWD. This inference is well supported but should not be relabeled as an explicit quota-accounting SLA. [OAuth DWD](https://developers.google.com/identity/protocols/oauth2/service-account#delegatingauthority), [migration best practices](https://knowledge.workspace.google.com/admin/getting-started/google-drive-large-migration-best-practices)

**Other daily caps:** No additional general daily **upload-byte** ceiling per shared drive, Workspace organization, Cloud project or direct service account was identified in the reviewed upload-limit documents **[UNVERIFIED, not proof none exists]**. The current API page separately documents **1 TB/day/project egress before charges**, a **400,000,000 quota-unit/day billing threshold**, request-rate quotas and additional backend throttling. Egress is not ingress; neither billing threshold should be represented as an extra hard daily migration-upload cap. Organization storage and administrator-defined shared-drive storage caps also apply. [API limits](https://developers.google.com/workspace/drive/api/guides/limits), [shared-drive limits](https://support.google.com/a/users/answer/7338880?hl=en)

### New users versus new customers

A newly created user can sign in to Google services after creation; the user-creation page's possible **24 hours** concerns appearing in the searchable Directory, not a documented upload warm-up. **[UNVERIFIED]** No reviewed primary source establishes a lower byte allowance, required account age, or guaranteed immediate 750-GB capability for a new user in an established paid domain. Treat 750 GB as a maximum, not day-one committed throughput. [Add a user](https://knowledge.workspace.google.com/admin/users/add-an-account-for-a-new-user), [upload limits](https://developers.google.com/workspace/drive/api/guides/limits)

New-subscription capacity is distinct: **“Pooled storage is granted in stages”**; the storage page says the full storage limit becomes available after a **$30 USD subscription payment**, and increases can take **72 hours** after payment. **[UNVERIFIED]** A separate new-customer daily upload-bandwidth cap was not established by that source. [Storage and upload limits](https://knowledge.workspace.google.com/admin/drive/storage-and-upload-limits-for-google-workspace)

## 2. One service account, many delegated subjects, one project quota

### Authorization and identity

The documented DWD setup registers the service account's **client ID** and allowed **OAuth scopes** in Admin console once. The app then selects each user using `createDelegated(...)`, `with_subject(...)`, or JWT `sub`. Google's wording: **“Your application now has the authority to make API calls as users in your Workspace domain (to ‘impersonate’ users).”** There is no per-subject registration step in that procedure. This is broad authority; it is not limited to just the 20 users by the DWD registration itself. [Google OAuth service-account guide](https://developers.google.com/identity/protocols/oauth2/service-account#delegatingauthority)

Drive-only scope is sufficient for the documented shared-drive creation API. It does not create users, buy licenses, grant them drive membership, or confer administrator privileges. The user must have the appropriate edition/service access, creation permission and shared-drive role. **[INFERENCE]** Those administrative provisioning steps are separate from Migmate's Drive-only credentials. [Shared-drive prerequisites](https://developers.google.com/workspace/drive/api/guides/manage-shareddrives), [Drive setup/access](https://knowledge.workspace.google.com/admin/drive/get-started-drive-setup-guide-for-admins)

### Important 2026 quota-model change

The current Drive API limits page, updated **2026-09-11**, publishes:

| Limit/threshold | Current published value |
|---|---:|
| Per minute per project | 1,000,000 **quota units** |
| Per minute per user per project | 325,000 **quota units** |
| Per day per project, egress before charges | 1 TB |
| Daily billing threshold | 400,000,000 **quota units** |

Source: [Drive API limits](https://developers.google.com/workspace/drive/api/guides/limits).

It charges different method weights: reads such as `files.get` **5 units**, lists such as `files.list` **100**, downloads such as `files.download` **200**, edits such as `files.update` **50**, and other actions such as `files.generateIds` **5**. Consequently there is no single current universal “queries/minute” value: **[INFERENCE, arithmetic]** one million units could represent 10,000 list calls/minute or 20,000 update calls/minute, before user limits, workload mix and backend enforcement. Do not automatically classify every upload/chunk/permission request by an example row; confirm its actual metric in the project's Console. [Per-method quota usage](https://developers.google.com/workspace/drive/api/guides/limits#per-method-quota)

**Do not reuse a legacy 12,000-queries/minute figure as today's universal default.** Google says quota changes began **May 1, 2026**, with different transition treatment for existing versus new projects, and that not all projects have the same quotas. Inspect the real service-account project's **APIs & Services → Drive API → Quotas & System Limits**. All 20 subjects still aggregate against that project. The current page also says standard API use remains free and billing details will be announced later in 2026 with at least 90 days' notice; do not invent a current price or treat a future billing threshold as a present hard refusal. [2026 standardized model](https://developers.google.com/workspace/tools-safety), [Drive limits/pricing](https://developers.google.com/workspace/drive/api/guides/limits), [view quotas](https://docs.cloud.google.com/docs/quotas/view-manage)

Google's limits page says API calls by a service account are considered a single account. Its error-resolution page separately recommends **DWD and `quotaUser`** where one user issues requests for many users. **[INFERENCE]** Do not conflate direct-SA identity with 20 properly delegated user identities, or assume 20 jobs automatically create 20 per-user buckets without examining the actual authentication/metric attribution. `quotaUser` is a request-quota accounting parameter, not a new Workspace user or a documented way to manufacture daily upload allowances. [Drive quota guide](https://developers.google.com/workspace/drive/api/guides/limits), [userRateLimitExceeded guidance](https://developers.google.com/workspace/drive/api/guides/handle-errors#user-rate-limit)

To request increases, select the relevant project/quota on **IAM & Admin → Quotas & System Limits**, choose **Edit**, enter the requested value, and submit justification. Approval is not guaranteed; larger requests can take longer. Quota Admin permissions are required. Google explicitly says the daily billing threshold cannot be increased. **[UNVERIFIED]** Request-quota adjustment documentation does not establish a mechanism to raise the 750-GB/user upload ceiling. [Quota management](https://docs.cloud.google.com/docs/quotas/view-manage#requesting_higher_quota), [Drive increase guidance](https://developers.google.com/workspace/drive/api/guides/limits#request_a_quota_increase)

## 3. Service accounts acting as themselves

Google Cloud IAM says:

> “Service accounts do not belong to your Google Workspace domain, unlike user accounts.”
>
> “Service accounts can't own Google Workspace assets. They can, however, create assets in a shared drive in the domain.”

Source: [Service accounts and Workspace domains](https://docs.cloud.google.com/iam/docs/service-account-overview#service_accounts_and_google_workspace_domains).

- **Existing shared drives:** direct service-account access is possible where the organization's sharing policy and granted permissions allow it; it does not require pretending the SA is a licensed internal human user. **[INFERENCE]** A directly granted SA member/file permission is an external identity for Workspace-domain purposes, not an internal user merely because its Cloud project belongs to the organization. [IAM](https://docs.cloud.google.com/iam/docs/service-account-overview), [shared-drive permission model](https://developers.google.com/workspace/drive/api/guides/about-shareddrives)
- **Creating shared drives:** the creation guide requires an authenticated user with a supported Workspace account and permitted organizational unit. **[INFERENCE]** A direct `gserviceaccount.com` identity does not meet that requirement; create as an eligible delegated Workspace user instead. The created drive automatically gives that user `organizer`. [Creation prerequisites](https://developers.google.com/workspace/drive/api/guides/manage-shareddrives)
- **`domainUsersOnly: true`:** the API says access to the drive **and its items** is restricted to users of the drive's domain. Combined with Google's explicit statement that SAs do not belong to that domain, **[INFERENCE]** direct SA access is excluded under that restriction. This is an access restriction, not merely a membership-list naming check. The field also notes that other sharing policies can override the restriction; do not assume a service-account-specific exception. A delegated `files@eidra.com` user is a different actor and can be eligible. [Drive restrictions](https://developers.google.com/workspace/drive/api/reference/rest/v3/drives), [IAM domain status](https://docs.cloud.google.com/iam/docs/service-account-overview)
- **Own 750 GB allowance:** **[UNVERIFIED]** no reviewed primary source grants each service account a separately guaranteed 750-GB/day upload entitlement. Google's byte-limit wording refers to Workspace users; its “single account” sentence concerns API request quotas. Do not build a quota-farming design by multiplying service accounts. Google's migration guide says not to use SAs to acquire additional storage quota or act as domain members. [Limits](https://developers.google.com/workspace/drive/api/guides/limits), [migration guidance](https://knowledge.workspace.google.com/admin/getting-started/google-drive-large-migration-best-practices)

**Documentation inconsistency:** the current [Create and manage files](https://developers.google.com/workspace/drive/api/guides/create-file#file_ownership) page describes service accounts owning dedicated Drive storage, contradicting the explicit IAM statement above and the [folder-limit guide](https://developers.google.com/workspace/drive/api/guides/folder#folder-limits), which says SAs cannot own files and must upload into shared drives or act for a human. Do not use the inconsistent ownership passage to promise free standalone service-account storage or upload capacity.

**Integration caveat:** the current `drives` resource documentation explicitly says restrictions **cannot be set when creating a shared drive**; first create it, then use `drives.update`. This is relevant to the supplied description that Migmate creates domain-only drives, but this research did not inspect or modify implementation and does not claim the existing call sequence is wrong. [Drive restrictions field](https://developers.google.com/workspace/drive/api/reference/rest/v3/drives)

## 4. Policy: affirmative migration guidance, with real caveats

### Google explicitly recommends distributing migration writes

The large-migration guide covers hundreds of thousands of files from third-party systems. It says:

> “Using service accounts can help you complete your migration faster by spreading the migration load across many users.”
>
> “To speed up uploading content to Google Drive and avoid quota issues, use a service account with domain-wide delegation to distribute write activity across many different impersonated users.”
>
> “Only use service accounts for delegation where the identity is that of an individual user.”
>
> “Do not use service accounts to acquire additional storage quota or act as members of a domain.”

It recommends putting uploaded content into shared drives or assigning ownership to user accounts, and working with a Google partner or Workspace support for large migrations. **[INFERENCE]** The proposed one-SA/many-user architecture is close to this documented recommendation; it is not equivalent to manufacturing SA-owned storage. [Google Drive large migration best practices](https://knowledge.workspace.google.com/admin/getting-started/google-drive-large-migration-best-practices)

### Temporary licensed users are explicitly recommended in Workspace Migrate

For SharePoint migration sharding Google says:

> “Use a sharding users list even if you intend to migrate the content to multiple shared drives.”
>
> “We recommend that you set up temporary Google Workspace users using an easily identifiable username, such as shard-user1. Use the new accounts for your sharding users list. Then, delete the users after you complete the migration.”

Those users must have licenses throughout migration, matching **the highest version of the Workspace edition assigned to the target domain**. Recommended sharding-user count is the larger of **one account per 400,000 files** or **10 accounts per node**. **[INFERENCE, arithmetic]** The file-count rule alone yields **43–63 accounts** for 17–25M files. This is Workspace Migrate-specific guidance—not a hard Drive limit and not proof rclone requires that number. [Set up sharding users](https://support.google.com/workspacemigrate/answer/9326912?hl=en)

Google also advises additional target GUser accounts for SharePoint → shared drives, at least **one target GUser per active node server**. [SharePoint migration best practices](https://support.google.com/workspacemigrate/answer/9231435?hl=en)

### Terms do not disappear because sharding is documented

| Primary policy | Relevant wording |
|---|---|
| [Google APIs Terms §2(d)](https://developers.google.com/terms) | “You agree to, and will not attempt to circumvent, such limitations documented with each API.” Above-limit use requires express consent. |
| [Workspace/Cloud terms §3.3(d)(iii)](https://workspace.google.com/intl/en/terms/premier_terms/) | Prohibits use intended to avoid fees or “to circumvent Service-specific usage limits or quotas.” |
| [Workspace AUP](https://workspace.google.com/intl/en/terms/use_policy/) | Prohibits altering/disabling/interfering with/circumventing aspects of the service. Also prohibits creating **“End User Accounts assigned to business functions rather than to human beings for the purpose of sharing files within or outside of the domain.”** |
| [Drive/Docs abuse policy, Circumvention](https://support.google.com/docs/answer/148505?hl=en) | Prohibits bypassing policies/restrictions, including creating/using multiple accounts to engage in previously prohibited behavior. |
| [Disabled-account guidance](https://support.google.com/drive/answer/40695?hl=en) | “Don't create or use multiple accounts to break Google's policies”; also acknowledges legitimate multiple-account use. |

The current terms page says the integrated terms take effect at the next renewal and separately signed agreements can govern. **[UNVERIFIED]** The exact governing contract for this tenant was not available. **[INFERENCE]** Distinguish Google's recommended sharding while respecting each actor's limits from circumventing a restriction. The explicit temporary-sharding recommendation is strong evidence against “all multiple migration accounts are forbidden”; it is not blanket approval of any function-account quota scheme. Written Google/reseller confirmation should cover the exact third-party implementation, temporary identities, edition mix and expected throughput. [Terms](https://workspace.google.com/intl/en/terms/premier_terms/), [AUP](https://workspace.google.com/intl/en/terms/use_policy/), [sharding recommendation](https://support.google.com/workspacemigrate/answer/9326912?hl=en)

### Google's tools do not establish a 750-GB exemption

**[UNVERIFIED]** No reviewed Workspace Migrate/current data-import page grants an exemption from the ordinary upload/copy byte ceiling. API quota increase guidance is not a promise to increase that ceiling. [Drive limits](https://developers.google.com/workspace/drive/api/guides/limits), [large-migration guidance](https://knowledge.workspace.google.com/admin/getting-started/google-drive-large-migration-best-practices)

As of the September 21, 2026 release notes, **Workspace Migrate OneDrive/SharePoint migrations become unavailable after December 15, 2026**; its SharePoint documentation says it no longer receives updates/fixes. Its sharding advice remains useful evidence, but it is not a long-term product choice without checking the cutoff. [Release notes](https://support.google.com/workspacemigrate/answer/9222863?hl=en), [SharePoint guidance](https://support.google.com/workspacemigrate/answer/9231435?hl=en)

Current Admin-console SharePoint import is not merely email migration: the default method uses **Google's shared API quota**, handles up to **1,000 sites at a time**, and maps to target GUsers with Manager permission; the advanced method uses **your own dedicated API quota**, configures an Azure application, handles **5,000 sites per batch**, and permits **5–7 concurrent batches** depending on Microsoft licenses. Both establish DWD/client ID for Data import. **[INFERENCE]** “Dedicated API quota” does not prove increased Google destination byte quota, especially where setup includes the source Azure application. [Default SharePoint import](https://knowledge.workspace.google.com/admin/migrate/migrate-files-from-a-sharepoint-online-account), [Advanced SharePoint import](https://knowledge.workspace.google.com/admin/migrate/advanced-import-for-sharepoint-online)

## 5. Deleting temporary users: content, access and identity

### Content and ownership transfer

Google explicitly lists **“Files in shared drives”** under what is **not deleted** with a user, because the organization owns them. The deletion transfer workflow excludes shared-drive files. Therefore **no user-to-user Drive ownership transfer is required for content already in shared drives**. Any My Drive files created accidentally by those accounts are a separate deletion/transfer concern. [Delete/remove a user](https://knowledge.workspace.google.com/admin/users/delete-or-remove-a-user-from-your-organization#what_gets_deleted), [shared-drive ownership](https://developers.google.com/workspace/drive/api/guides/about-shareddrives)

### Last Manager/organizer

Google documents shared drives with no organizers: only administrators can manage them. With no members, shared-drive access requires administrative recovery, although directly shared item permissions can still permit access to those items. Admins with the Drive & Docs privilege can go to **Apps → Google Workspace → Drive and Docs → Manage shared drives → Manage members** and add/promote a permanent Manager. **[INFERENCE]** Deleting the last temporary Manager is not a content-deletion trigger, but leaving all drives managerless is an avoidable handoff failure. Assign permanent organizational managers before deleting uploader accounts; do not rely on the deleted identity remaining a useful member. [Troubleshoot shared drives](https://knowledge.workspace.google.com/admin/drive/troubleshoot-shared-drives-for-your-users), [organizer/member count rules](https://developers.google.com/workspace/drive/api/guides/about-shareddrives#member_and_organizer_count_rules)

### Revision/activity/last-modifier attribution

- Drive Activity API explicitly represents **“A user whose account has since been deleted”** as `User.deletedUser`; its `DeletedUser` object has **no fields**. This representation does not preserve the previous name/email/identifier. Do not generalize this exact representation to every Admin audit log or Drive UI surface. [Activity User schema](https://developers.google.com/workspace/drive/activity/v2/reference/rest/v2/activity/user)
- File and revision APIs expose `lastModifyingUser`, documented for modifications by a signed-in user. **[UNVERIFIED]** Their schemas do not state exactly which name, email, identifier or placeholder survives user deletion, nor the resulting version-history UI label. Do not promise “Deleted user” everywhere or preserved real-person attribution everywhere. [File schema](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), [Revision schema](https://developers.google.com/workspace/drive/api/reference/rest/v3/revisions)
- **[UNVERIFIED]** File survival alone does not establish preservation of every historic revision/attribution record. Independently, old binary-file versions may be deleted after **30 days or 100 newer versions** unless kept forever; `keepForever` supports at most **200 revisions per file**. [Activity and versions](https://support.google.com/drive/answer/2409045?hl=en), [Revision schema](https://developers.google.com/workspace/drive/api/reference/rest/v3/revisions)
- **[INFERENCE]** If uploader/source-author provenance matters, retain an independently durable migration identity mapping rather than depending on deleted-user display names. The same concern exists even if source authorship was never copied into Drive's last-modifier fields. [Deleted actors](https://developers.google.com/workspace/drive/activity/v2/reference/rest/v2/activity/user), [File metadata](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)

### Restore window

A deleted Workspace user can be restored for **20 days**; after that Google says restoration is unavailable. A suitable available license, available domain and no conflicting username are needed. Restoration normally takes up to **24 hours**, rarely up to **five days**. This is an account-restoration window, not a time limit on organization-owned shared-drive content. [Restore a deleted user](https://knowledge.workspace.google.com/admin/users/restore-a-recently-deleted-user)

## 6. Licensing, capacity and temporary-account cost

### Eligible licenses

The current shared-drive setup guide includes **Business Starter/Standard/Plus, Frontline Plus, Enterprise Standard/Plus, Education Fundamentals/Standard/Plus, Essentials/Enterprise Essentials/Enterprise Essentials Plus, Nonprofits and G Suite Business**. Creation can still be disabled by the administrator; upload requires Contributor (`writer`) or a higher suitable role. This is an eligibility list, not a promise every listed legacy/special-purpose edition can be purchased for migration accounts. [Shared-drive setup/licensing](https://knowledge.workspace.google.com/admin/drive/set-up-shared-drives-for-your-organization), [Drive roles](https://developers.google.com/workspace/drive/api/guides/about-shareddrives#roles_for_shared_drives)

**Business Starter does support shared drives**, including adding members/files/folders, but not all advanced default sharing/security controls. Some older/incomplete troubleshooting lists omit Starter; use the explicit current setup guide rather than treating that omission as prohibition. [Shared-drive setup](https://knowledge.workspace.google.com/admin/drive/set-up-shared-drives-for-your-organization)

**Cloud Identity Free/Premium, Frontline Starter/Standard and G Suite Basic** can be internal shared-drive members only as **Viewers** and **cannot upload**; direct file sharing may allow editing/commenting. The same guide permits more roles in external shared drives, which is not a drop-in substitute for this internal-domain design. **Essentials Starter** does not include shared drives; legacy Essentials is unavailable to new customers. [Licensing exceptions](https://knowledge.workspace.google.com/admin/drive/set-up-shared-drives-for-your-organization#licensing), [Essentials comparison](https://knowledge.workspace.google.com/admin/getting-started/editions/compare-essentials-editions#drive)

Starter is the **cheapest listed paid Business tier**, not a proven universally cheapest eligible or tenant-purchasable license. Standard USD prices shown by Google are **$8.40/user/month Flexible** or **$7/user/month Annual commitment**. **[INFERENCE, arithmetic]** Twenty Starter Flexible seats are **$168/full month** before discounts/taxes. **[UNVERIFIED]** The ability to mix 20 Starter seats into this domain's existing subscription, its negotiated price, and any reseller/mixed-SKU minimums require the actual offer; Google documents changing licenses where multiple subscriptions already exist, not a universal right to buy any mix. Also, Google's own Workspace Migrate sharding instructions specifically require the **highest target-domain edition**—do not advertise cheap Starter seats as compliant with that product prescription. [Plan comparison](https://knowledge.workspace.google.com/admin/billing/compare-flexible-and-annual-fixed-term-payment-plans), [multiple subscriptions](https://knowledge.workspace.google.com/admin/billing/change-a-users-license-to-a-different-subscription), [Migrate licensing](https://support.google.com/workspacemigrate/answer/9326912?hl=en)

### Flexible versus committed seats

| Billing model | Consequence for temporary migration users |
|---|---|
| **Flexible** | No commitment; users may be added/deleted at any time; mid-month additions/deletions are prorated. Google explicitly uses temporary seasonal workers as an example. Some add-ons can still incur a full month's charge. [Flexible Plan](https://knowledge.workspace.google.com/admin/billing/flexible-plan) |
| **Annual/Fixed-Term** | One-year-or-longer commitment to purchased license count. Deleting users does **not** lower the committed count/bill; seats can be reassigned and reductions occur at renewal. Added seats are prorated for the remaining term, not cancellable when migration ends. Early cancellation still leaves the remaining commitment payable. [Annual Plan](https://knowledge.workspace.google.com/admin/billing/annual-fixed-term-plan) |
| **New-account purchase limits** | Flexible documentation describes a **20–50-user initial limit** for accounts under **90 days**; a manual payment credited to invoices can enable more. | **Archived User** | Preserves account/service data and prevents sign-in; the active Workspace license becomes available for reassignment within 24 hours. Requires a matching AU edition/subscription. It is not a documented active-upload identity. Freeing a committed active seat does not cancel the contractual bill. [Archive former employees](https://knowledge.workspace.google.com/admin/users/archive-former-employee-accounts), [AU licenses](https://knowledge.workspace.google.com/admin/billing/add-archived-user-licenses) |

**[INFERENCE]** AU licensing is unnecessary solely to preserve organization-owned shared-drive files; consider it only for account-associated retention needs. **[UNVERIFIED]** AU documentation does not promise every historical UI/API attribution field remains unchanged. Google's deletion guide cautions against deletion merely to save licenses when user data needs retention, while Flexible billing explicitly supports deleting temporary-worker accounts. Neither alone resolves migration-function-account policy. [Deletion guidance](https://knowledge.workspace.google.com/admin/users/delete-or-remove-a-user-from-your-organization), [Flexible](https://knowledge.workspace.google.com/admin/billing/flexible-plan), [Archive users](https://knowledge.workspace.google.com/admin/users/archive-former-employee-accounts)

### Permanent storage must outlive the temporary accounts

Business pooled allowances are **30 GB/Starter user, 2 TB/Standard user, 5 TB/Plus user**, including applicable Archived Users. Shared-drive files consume the organization pool, not an uploader's personal My Drive capacity; a user can upload into shared drives even when their personal My Drive is full. The storage FAQ says storage is measured in binary units despite GB/TB labels. **[INFERENCE, arithmetic]** Twenty Starter seats contribute only **600 GiB**, not 80–120 TB. Upload capacity and storage entitlement are different dimensions. [Storage FAQ](https://knowledge.workspace.google.com/admin/storage/google-workspace-storage-faq-for-admins), [shared-drive storage](https://developers.google.com/workspace/drive/api/guides/about-shareddrives#availability_and_storage)

**[INFERENCE]** Removing temporary entitlements can reduce the available storage pool even though their shared-drive files survive. Maintain permanent capacity independently; exact quota-recalculation timing after deletion was not established. Google says exceeding organizational storage by **25% or for 14 days, whichever comes first**, prevents new Drive uploads and other operations. [Storage FAQ](https://knowledge.workspace.google.com/admin/storage/google-workspace-storage-faq-for-admins)

## 8. rclone behavior: fatal stop, credentials and request pacing

### Upload-limit behavior and units

rclone documents `--drive-stop-on-upload-limit` as **“Make upload limit errors be fatal.”** Its text says **“750 GiB”** and calls the limit undocumented; Google's current official docs say **“750 GB”** and explicitly document it. Preserve the distinction rather than silently using rclone's old wording as the authoritative Google quota specification. rclone warns detection depends on undocumented error-message strings and could break. Default is `false`; this deployment enables it. [rclone flag](https://rclone.org/drive/#drive-stop-on-upload-limit), [Google current wording](https://developers.google.com/workspace/drive/api/guides/limits)

With the flag set, a detected limit stops the in-progress sync as a fatal error. **[INFERENCE from documented behavior]** It does not itself wait for quota recovery, schedule tomorrow's restart, balance remaining subject allowance, or rotate accounts. A fatal quota stop therefore remains a job-control concern rather than evidence that a migration has finished. [rclone upload-limit flag](https://rclone.org/drive/#drive-stop-on-upload-limit)

### Subject and service-account file are separate knobs

- `--drive-impersonate user@example.com` selects the impersonated user when using an SA; rclone's `impersonate` configuration value is a **string email**, not a boolean. Migmate's supplied `impersonate = true` is an application-level convention and should not be confused with rclone's raw option type. rclone source sets `conf.Subject = opt.Impersonate`. [Impersonate option](https://rclone.org/drive/#drive-impersonate), [Drive source](https://github.com/rclone/rclone/blob/master/backend/drive/drive.go)
- `--drive-service-account-file /path/account.json` chooses the service-account credentials. rclone also supports inline service-account credentials. One credential file can be used for different subjects in separate remotes/jobs. [Service-account configuration](https://rclone.org/drive/#service-account-support)
- Backend runtime commands include `rclone backend get drive: -o service_account_file` and `rclone backend set drive: -o service_account_file=sa.json`; RC equivalents use `backend/command command=get|set fs=drive:`. The backend set command documents SA-file and chunk-size changes, not an automatic rotation policy or a runtime subject-changing command. [Drive backend commands](https://rclone.org/drive/#backend-commands)
- Source confirms SA-file switching rebuilds the authenticated client with the existing options, including the current impersonated subject. **[INFERENCE]** Rotating SA JSON files while retaining `files@eidra.com` does not implement user sharding or provide an extra user upload allowance. [changeServiceAccountFile/getServiceAccountClient](https://github.com/rclone/rclone/blob/master/backend/drive/drive.go)
- RC `config/create`/`config/update` create/update a remote's stored configuration. RC `fscache/clear` exists because backends are cached and changes may require recreating a backend. **[INFERENCE]** Do not assume a generic config edit seamlessly changes an already-running transfer's identity; use explicitly separated per-subject job configurations for predictable accounting. [config/update](https://rclone.org/rc/#config-update), [fscache/clear](https://rclone.org/rc/#fscache-clear)
- RC access is equivalent to shell access as the rclone process user; keep it restricted and authenticated if used for runtime changes. [RC security](https://rclone.org/rc/#security)

### Pacing is per backend instance, not per upload worker

Documented defaults are:

| Setting | Default | Meaning |
|---|---:|---|
| `--drive-pacer-min-sleep` | **100ms** | Minimum interval used by the Drive API pacer. |
| `--drive-pacer-burst` | **100** | Calls allowed without sleeping. |

Sources: [minimum sleep](https://rclone.org/drive/#drive-pacer-min-sleep), [burst](https://rclone.org/drive/#drive-pacer-burst).

The Drive backend constructs a pacer in each `Fs`; the GoogleDrive pacer uses `rate.NewLimiter(rate.Every(minSleep), burst)` and exponential backoff on retries. **[INFERENCE from source]** At 100ms, that is approximately **10 paced calls/sec sustained**, with a **100-call burst**, per backend instance; raising transfer-worker count does not multiply the same instance's pacer. Twenty independent target backends could nominally issue roughly **200 paced calls/sec aggregate**, but all still share the Cloud project quota, and Google backend/user throttles can reduce it. This is not a bytes/sec guarantee and not a claim every HTTP body chunk is necessarily counted by the same pacer. [Drive pacer construction](https://github.com/rclone/rclone/blob/master/backend/drive/drive.go), [GoogleDrive pacer implementation](https://github.com/rclone/rclone/blob/master/lib/pacer/pacers.go)

`--fast-list` trades more memory for fewer listing transactions by combining directory queries. It does **not** raise byte quotas, project quotas or per-drive item caps. [rclone fast-list](https://rclone.org/drive/#fast-list)

**[INFERENCE, sizing only]** At a nominal 15 TB/day, 80–120 TB takes **5.3–8 days of pure byte-budget time**, before enumerations, folders, permissions, retries, delta passes or source limits. Moving 17–25M files over that broad duration envelope needs roughly **25–54 successful file completions/sec aggregate**. Whether ~200 paced calls/sec is sufficient depends on actual calls per file and workload mix; multiple metadata writes and list calls can make request work the controlling Google-side bottleneck even when upload bytes remain. Request quotas are weighted in current docs, so do not compare raw request counts to quota units. [Upload/request limits](https://developers.google.com/workspace/drive/api/guides/limits), [rclone pacing](https://rclone.org/drive/#drive-pacer-min-sleep)
