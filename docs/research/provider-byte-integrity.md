# Provider byte-integrity research

This note captures the SharePoint and Google Drive behavior that matters when a migration verifier compares uploaded and downloaded bytes.

## Recommendation

- **SharePoint can change document bytes without a user editing the document body.** Microsoft documents property demotion: library-column values are written into document properties and the updated document is saved. rclone independently documents resulting SharePoint Office-file size/hash failures. The detailed Microsoft parser description is archived SharePoint Foundation documentation, not a complete current SharePoint Online specification; rclone is a primary source for its own operational observations, not Microsoft's service contract. [Microsoft property promotion/demotion](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29), [rclone SharePoint caveat](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint)
- **Google Drive does not document analogous automatic property writeback for ordinary binary uploads without conversion.** Its API distinguishes raw binary blobs from Google-native documents, downloads blob content with `files.get?alt=media`, and exposes content checksums. This supports expecting byte identity for unconverted Office files, PDFs, and images; it is not an unconditional guarantee against edits, conversion, client-side processing, or service defects. No primary-source evidence of routine EXIF stripping or Office-package rewriting by this upload/download path was found. [Google download semantics](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [File resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), [Upload and conversion](https://developers.google.com/workspace/drive/api/guides/manage-uploads)
- **SharePoint → Google Shared Drive: retain strict SHA-256 verification of the actual source stream transferred.** A SharePoint file might already differ from an earlier pre-SharePoint original, or its download might carry protection. That does not justify Google changing the bytes actually supplied to it. Distinguish source metadata/download discrepancies from destination corruption. This is a verifier recommendation inferred from the documented provider behaviors, not a provider guarantee. [SharePoint rewriting](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint), [SharePoint download protection](https://learn.microsoft.com/en-us/purview/sensitivity-labels-sharepoint-onedrive-files), [Google blob downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads)
- **Google Drive → SharePoint: expect some legitimate whole-file SHA-256 and size mismatches, but do not silently pass them.** Record a named provider-transformation finding, retain the original hash and the downloaded destination hash, and require evidence and human acceptance. “Office document” alone does not prove a mismatch is harmless. This is a proposed verification policy grounded in Microsoft's documented writeback and rclone's observed failures. [Property demotion](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29), [rclone caveat](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint)

## Evidence boundaries

The strongest sources have different scopes: current Graph and Drive references specify API fields; current Purview documentation specifies labeling/protection; Microsoft's detailed parser documentation applies to SharePoint Foundation 2010; rclone documents operational SharePoint failures. Do not turn an archived mechanism or a tool observation into a universal current-cloud file-type matrix. In particular, rclone explicitly scopes its Office-mutation warning to SharePoint, **not OneDrive or OneDrive for Business**; current Microsoft labeling documentation separately establishes protection behavior for both SharePoint and OneDrive. [Graph hashes](https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0), [Archived parser scope](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29), [rclone scope](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint), [Current labeling scope](https://learn.microsoft.com/en-us/purview/sensitivity-labels-sharepoint-onedrive-files)

No authenticated tenant experiment was performed. Behaviors marked **unverified** below must not be presented as measured facts or used to automatically waive integrity findings.

## SharePoint mechanisms and timing

### Property promotion, demotion, and content types

**Promotion** extracts document-property values into matching library columns. **Demotion** performs the reverse operation, writing column values into the document. Promotion alone describes extraction, not necessarily a byte rewrite; demotion explicitly modifies the document and saves it when changes occur. Applicable properties are determined by the document's content type, or the library columns when there is no content type. [Microsoft property promotion/demotion](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29)

Microsoft's archived description lists four triggers: file upload; changes to the associated list-item fields; programmatic updates to `SPFile.Properties`; and the first download after the list schema changes. The document parser can also update content-type information and perform link discovery/repair. Thus, “only at upload” and “only `docProps` can change” are both too strong. These are documented historical mechanisms; their exhaustive current SharePoint Online implementation is **unverified**. [Triggers](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29), [Parser responsibilities](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa544149%28v%3Doffice.14%29)

### Document IDs and retention labels

The historical Document ID service adds metadata columns to document/document-set content types and assigns IDs to documents. Combined with the demotion mechanism, this is a reason to investigate added metadata in a package diff. **Inference, not an established current-cloud guarantee:** enabling Document IDs may contribute to relevant writeback; the reviewed documentation does not prove that every ID assignment rewrites every file format. [Document IDs and content types](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/ee559302%28v%3Doffice.14%29), [Demotion rules](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29)

Retention labels govern retention, deletion, and record behavior; they are not synonymous with sensitivity-label encryption. Microsoft documents retention labeling through SharePoint metadata and CSOM methods. A universal claim that applying a retention label itself rewrites the downloadable binary is **unverified**; equally, do not assume all metadata writes are byte-neutral when property demotion can apply. [Retention behavior](https://learn.microsoft.com/en-us/purview/retention-policies-sharepoint), [Retention-label CSOM methods](https://learn.microsoft.com/en-us/sharepoint/dev/apis/csom-methods-for-applying-retention-labels), [Property demotion](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29)

### Sensitivity labels, IRM, and encryption at rest

Sensitivity labels and their encryption can remain with downloaded Office/PDF files. SharePoint IRM is explicitly described as applying encryption and restrictions **when users download files**; for Office/PDF files not encrypted by a sensitivity label, library IRM settings apply. Therefore, download-time protection is a separate mechanism from stored-document property demotion. The cited documentation does not promise deterministic identical encrypted bytes across repeated downloads or identical behavior for every app-only endpoint. [Sensitivity labels and IRM precedence](https://learn.microsoft.com/en-us/purview/sensitivity-labels-sharepoint-onedrive-files#information-rights-management-irm-options-and-sensitivity-labels)

Microsoft also documents a library sensitivity-label configuration that extends SharePoint permissions to downloaded documents. This reinforces the need to inventory protection settings, not merely file extensions. Its applicability to a specific migration identity and download route requires validation; this note does not assert universal Graph/app-only coverage. [Extend protection on download](https://learn.microsoft.com/en-us/purview/sensitivity-labels-sharepoint-extend-permissions)

Encryption **at rest** is different: SharePoint stores encrypted chunks and reconstructs/decrypts a requested file inside the service. It is not, by itself, evidence of an Office-package rewrite or a reason to expect encryption-at-rest ciphertext in an ordinary download. [OneDrive and SharePoint encryption at rest](https://learn.microsoft.com/en-us/purview/data-encryption-in-odb-and-spo)

### Hashes, repeated downloads, and size

A changed document byte stream need not match the upload's SHA-256, and rclone explicitly reports size as well as hash mismatches. A size change is possible, not necessary: different bytes can have equal length. The latter is an elementary verifier inference, not a special provider behavior. [rclone failure description](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint)

The reviewed sources do **not** establish that every download of an unchanged, unprotected SharePoint item generates different bytes. The archived first-download-after-schema-change trigger describes saving an updated document, not unconditional randomization on every read. Protection applied at download creates additional uncertainty, but no cited contract states that two protected downloads must differ. Treat repeat-download stability as **unverified per configuration**, not as a universal defect. [Demotion lifecycle](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29), [Download-time IRM](https://learn.microsoft.com/en-us/purview/sensitivity-labels-sharepoint-onedrive-files#information-rights-management-irm-options-and-sensitivity-labels)

**Recommendation:** distinguish the uploaded byte count, provider-reported size, and downloaded byte count in evidence. rclone notes both mutation-related size failures and other inconsistent-size situations; do not assume a size field is always the exact length of a policy-transformed download. [rclone size caveats](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint)

## Microsoft Graph hashes

| Property       | Documented contract and consequence                                                                                                                                                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `quickXorHash` | Proprietary file-content hash, represented as Base64. Microsoft's note identifies it as the only hash guaranteed for both OneDrive work/school and home. Use it as provider metadata, not as a replacement for SHA-256. [Graph hashes](https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0) |
| `sha1Hash`     | SHA-1 of file contents **if available**; hexadecimal representation. Its presence in the schema is not a SharePoint/Business availability guarantee. [Graph hashes](https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0)                                                                    |
| `sha256Hash`   | Explicitly **unsupported: “Don't use.”** A migrator needing SharePoint SHA-256 must calculate it from a retrieved stream rather than relying on this field. [Graph hashes](https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0)                                                             |
| `crc32Hash`    | CRC32 **if available**; hexadecimal representation. No general SharePoint/Business availability guarantee. [Graph hashes](https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0)                                                                                                              |

The resource describes hashes of the file/current contents, not a retained receipt of the originally uploaded bytes. **Inference:** if demotion changes the stored file, its current-content hash should describe that representation. However, the reviewed Graph contract does not specify hash recalculation timing around demotion, nor guarantee correspondence to a download-time encrypted representation. Do not elevate that inference into a consistency guarantee. [Graph hash contract](https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0), [Stored-document update](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29), [Download protection](https://learn.microsoft.com/en-us/purview/sensitivity-labels-sharepoint-onedrive-files)

## Can a migrator disable modification?

- **`SPWeb.ParserEnabled`-style guidance must be scoped carefully.** Microsoft documents `ParserEnabled` in web-template/deployment schemas; the template setting controls adding library-column values to uploaded documents. That does not establish an app-only switch for an existing modern SharePoint Online library or a guarantee against labeling/IRM. [WebTemplate schema](https://learn.microsoft.com/en-us/sharepoint/dev/schema/webtemplate-element-web-template), [Web deployment schema](https://learn.microsoft.com/en-us/sharepoint/dev/schema/web-element-deploymentmanifest)
- **There is a public CSOM `List.ParserDisabled` property.** The reference exposes a remote Boolean getter/setter but supplies no behavioral explanation, supported Online operating procedure, permissions contract, or byte-preservation guarantee. Therefore, neither “there is no parser setting anywhere” nor “set this and Online is byte-preserving” is justified by this reference. App-only effectiveness and supportability remain **unverified**. [CSOM property](https://learn.microsoft.com/en-us/dotnet/api/microsoft.sharepoint.client.list.parserdisabled?view=sharepoint-csom)
- **No documented Graph no-mutation upload option was found.** Simple content upload and upload sessions do not document a property-demotion bypass; upload-session `deferCommit` controls final commit, not downstream parsing or policy processing. Changing APIs is not a substantiated preservation strategy. [Content upload](https://learn.microsoft.com/en-us/graph/api/driveitem-put-content?view=graph-rest-1.0), [Upload sessions](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0)
- **Recommendation:** do not make parser administration a prerequisite or quietly alter organizational protection policies. A controlled library configuration might reduce transformations, but a supported, universal SharePoint Online app-only byte-preservation mode was not established by the reviewed references. Obtain provider confirmation and controlled evidence before claiming one. [CSOM reference limitations](https://learn.microsoft.com/en-us/dotnet/api/microsoft.sharepoint.client.list.parserdisabled?view=sharepoint-csom), [Independent download protection](https://learn.microsoft.com/en-us/purview/sensitivity-labels-sharepoint-onedrive-files)

## What established migration tools establish

### rclone

rclone's OneDrive backend explicitly recommends `--ignore-checksum --ignore-size` for affected SharePoint files. This suppresses checks; it does **not** validate that the changes are only harmless metadata. The same section suggests opening certain problematic files in the web interface to obtain a functionally equivalent representation without the discrepancy; that deliberately modifies the file and is not a transparent integrity-preserving operation. [rclone troubleshooting](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint)

From rclone 1.62 onward, its documented default for all OneDrive backends is QuickXorHash; prior Personal behavior used SHA-1. The docs describe `--onedrive-hash-type` for hash selection and permit `--checksum`, but neither setting prevents provider mutation. [rclone hash behavior](https://rclone.org/onedrive/#modification-times-and-hashes)

### SharePoint Migration Tool and Migration Manager

SPMT documents scanning access and known issues, packaging files with a manifest, uploading, and importing. Its incremental-migration documentation calls path-based matching for file shares and list-item-GUID matching for SharePoint sources “validation,” and considers modification timestamps. That is identity/incremental-selection logic, not a documented cryptographic proof that destination downloads equal source bytes. [SPMT workflow](https://learn.microsoft.com/en-us/sharepointmigration/how-the-sharepoint-migration-tool-works), [SPMT incremental validation](https://learn.microsoft.com/en-us/sharepointmigration/spmt-create-task)

The documented SPMT and Migration Manager file-share report schemas expose statuses, errors, item sizes, paths, and IDs, but no source-versus-downloaded-destination SHA-256 result. This is a statement about the public report contract, **not** proof that the tools perform no internal transport checks. A successful import/report row must not be reinterpreted as a whole-file SHA-256 equality certificate. [SPMT reports](https://learn.microsoft.com/en-us/sharepointmigration/using-the-sharepoint-migration-tool-reports), [Migration Manager reports](https://learn.microsoft.com/en-us/sharepointmigration/mm-reports)

No Microsoft-endorsed post-migration Office normalization algorithm or blanket permission to ignore Office hash mismatches was found in the reviewed migration guidance. Microsoft's documented reports and incremental rules do not supply such an algorithm. Claims that Microsoft recommends excluding `docProps` or `customXml` for migration integrity would therefore be **unverified**. [SPMT reports](https://learn.microsoft.com/en-us/sharepointmigration/using-the-sharepoint-migration-tool-reports), [SPMT task guidance](https://learn.microsoft.com/en-us/sharepointmigration/spmt-create-task)

## Google Drive binary integrity

### Ordinary uploads without conversion

Google describes blob files as raw binary files, including images, videos, and PDFs, and specifies `files.get` with `alt=media` for downloading their content. Conversion is a distinct upload operation selected by a Google Workspace MIME type. The defensible expectation for an Office/PDF/image blob uploaded without conversion is preservation of the supplied content, not automatic document-property synchronization. This is an inference from the API model; an explicit universal no-transformation warranty was not found. [Download guide](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [Upload/conversion guide](https://developers.google.com/workspace/drive/api/guides/manage-uploads)

Drive exposes image metadata, including EXIF time and camera information, as output-only metadata. The reviewed API reference does not describe deleting EXIF or rewriting the image on ordinary blob upload/download. Metadata extraction is not evidence of modifying the file. Google Photos compression/export behavior should not be substituted for this Drive API contract. [Image metadata fields](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), [Drive blob definition](https://developers.google.com/workspace/drive/api/guides/manage-downloads)

**Zero-byte files:** no provider rule requiring a zero-byte binary upload to become nonzero was found. Nevertheless, the reviewed upload guide does not establish every zero-length resumable-upload edge case; no live round trip was performed. Recommendation: test the adapter's empty-file path explicitly and require downloaded byte count zero plus the locally calculated empty-stream SHA-256. Do not confuse an empty resumable-session response body with successful storage of an empty file. [Upload protocol](https://developers.google.com/workspace/drive/api/guides/manage-uploads), [File size/checksum fields](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)

### Checksums and size

| Field            | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `md5Checksum`    | Output-only MD5 checksum of file content, applicable to binary content stored in Drive. [File reference](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)                                                                                                                                                                                                                                            |
| `sha1Checksum`   | Output-only SHA-1 associated with the file **if available**; populated only for content stored in Drive, not Docs Editors or shortcuts. [File reference](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)                                                                                                                                                                                            |
| `sha256Checksum` | Output-only SHA-256 with the same availability/content caveats. Missing is not a successful comparison; calculate a download hash when independent verification is required. [File reference](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)                                                                                                                                                       |
| `size`           | Current reference: size in bytes of blobs **and Google Workspace editor files**; absent for sizeless items such as shortcuts and folders. A native document's size is not a promise of its exported Office/PDF byte count. [File reference](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), [Separate export operation](https://developers.google.com/workspace/drive/api/guides/manage-downloads) |

### Cases that are not an ordinary blob round trip

- **Google-native documents:** uploaded content can be imported into a Google-native representation; `files.export` produces a requested export format rather than retrieving the original upload. Whole-file equality to the original Office/PDF input is not the right contract. [Conversion](https://developers.google.com/workspace/drive/api/guides/manage-uploads), [Downloads versus exports](https://developers.google.com/workspace/drive/api/guides/manage-downloads)
- **Shortcuts:** these are references with target metadata, not independent uploaded blob copies; checksum fields are not populated as though they were binary targets. Resolve and handle the target explicitly rather than treating the shortcut as an empty file. [Shortcut and checksum fields](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)
- **Labels and DLP:** Drive exposes labels as metadata, and DLP can apply labels and restrict download/printing/copying. The reviewed documentation does not describe these operations as returning a rewritten or redacted binary through `alt=media`. Check `capabilities.canDownload`; a blocked download is an access/verification failure, not an acceptable content mismatch. [File labels/capabilities](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), [DLP actions](https://support.google.com/a/answer/9655387), [Download prerequisite](https://developers.google.com/workspace/drive/api/guides/manage-downloads)
- **Client-side encryption:** the current File resource exposes encryption details needed by clients to decrypt content. Do not compare an application's plaintext hash with an encrypted payload hash and call that ordinary upload corruption; the representation boundary must be explicit. This is a verifier inference, not evidence that Drive silently encrypts otherwise ordinary uploads into a different downloadable blob. [Client encryption fields](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)

No reviewed primary source documents ordinary, unchanged, unconverted blobs returning different `alt=media` content merely because they are Office files, PDFs, images, labeled, or DLP-scanned. This is a bounded research finding, not a proof that no service bug or unreviewed policy feature can exist. [Blob download contract](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [File resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)

## Verification options and tradeoffs

The following are proposed verifier policies, not claims that either provider endorses a particular normalization scheme.

| Option                                                   | What it establishes and what it loses                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Exact source-stream and destination-download SHA-256** | Strongest direct whole-stream comparison; preserves detection of all byte changes, including legitimate SharePoint transformations. Costs a destination read and may be blocked by policy. Keep this as the default. [Blob download semantics](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [SharePoint transformation evidence](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint)                                                                                                                                                                                                                                                                                           |
| **Provider checksum comparison**                         | Useful corroboration of stored content when populated. Google SHA-256 can be compared with the source stream hash; Graph SHA-256 cannot. Provider hashes are not independent proof of a separately policy-transformed download. [Google fields](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), [Graph limitations](https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0), [IRM](https://learn.microsoft.com/en-us/purview/sensitivity-labels-sharepoint-onedrive-files)                                                                                                                                                                                                           |
| **Named, human-accepted transformation finding**         | Preserves the fact that exact identity failed while allowing an authorized person to accept documented metadata/protection changes. Record original and destination hashes/counts, affected parts or protection evidence, and the acceptance rationale. Do not classify solely by extension. [Demotion mechanism](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29), [Download protection](https://learn.microsoft.com/en-us/purview/sensitivity-labels-sharepoint-onedrive-files)                                                                                                                                                                                         |
| **OOXML package-level comparison**                       | Comparing decompressed package parts can separate packaging differences from part-content changes; narrowly specified XML normalization can then support a logical-equivalence finding. This is not whole-file identity, requires format-aware handling, and does not apply to legacy binary Office formats or encrypted containers without additional processing. [Open XML package model](https://learn.microsoft.com/en-us/office/open-xml/about-the-open-xml-sdk)                                                                                                                                                                                                                                                                      |
| **Blanket exclusion of `docProps` or `customXml`**       | Not recommended. Custom XML can contain application data and Office-defined content-type information; ignoring whole directories can hide meaningful loss. Prefer a reviewed allowlist of specific observed property changes and retain evidence of all excluded differences. No provider-approved migration allowlist was found. [Custom XML part API](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.packaging.customxmlpart), [Office-defined custom XML](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/52769434-bde1-4e81-a128-7001873acb2b), [Parser responsibilities](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa544149%28v%3Doffice.14%29) |
| **Size plus modified time**                              | Useful inventory/incremental signals, not content-integrity proof: timestamps can be set, and size can change due to the provider or remain equal despite different content. Using them alone deliberately lowers assurance and can still fail on transformed Office files. [rclone timestamps](https://rclone.org/onedrive/#modification-times-and-hashes), [rclone size failures](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint), [SPMT incremental rules](https://learn.microsoft.com/en-us/sharepointmigration/spmt-create-task)                                                                                                                                                                     |
| **Rebaseline destination after processing**              | A downloaded destination hash can detect later changes relative to that baseline, but cannot prove the transformation from source to destination preserved intended content. It supplements an accepted finding; it must not erase the original mismatch. This is a logical consequence of the documented representation changes. [Demotion lifecycle](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29)                                                                                                                                                                                                                                                                   |

**Recommended evidence boundary:** hash and count the exact stream handed to the destination; finish metadata writes that might trigger processing; then retrieve destination metadata and content and record both. For suspected transformations, compare repeat downloads and inspect package differences without presuming stability or harmlessness. Keep size, SHA-256, timestamps, MIME type, and provenance findings separate: content equality does not establish metadata equality, and metadata equality does not establish content equality. This is a proposed migration policy based on the providers' separate content/metadata models and SharePoint's metadata-triggered writeback. [SharePoint triggers](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/aa543341%28v%3Doffice.14%29), [Google content and metadata fields](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)

## What remains unverified

The reviewed primary sources do not settle an exhaustive current SharePoint Online/OneDrive for Business per-extension mutation matrix; a universally supported app-only parser bypass; exact Graph hash-refresh timing after demotion; repeat-download byte stability under every protection policy; or all zero-length Drive resumable-upload cases. These are explicit evidence gaps, not grounds to waive mismatches. Archived parser behavior, current API contracts, and tool-maintainer observations should remain distinct in both documentation and acceptance decisions. ## Consequences in this codebase (checked 2026-10-01)

- **Drive → SharePoint is not implemented.** The credential loader accepts only an `onedrive` document-library source and a `drive` service-account destination, and the engine knows two route names; a SharePoint destination refuses rather than degrades (`docs/release-limits.md` §5).
- **SharePoint → Drive hashes what SharePoint actually serves.** Execute stages the source stream and records its SHA-256 (`src/engine/drivers/file-state.ts` `stageSource`); verify re-reads the source, re-hashes it, and compares with Drive's `sha256Checksum`, falling back to `content_verification_degraded` when Drive withholds one (`src/engine/drivers/file-migration.ts` `verifyItem`). A file SharePoint rewrote years ago is copied as SharePoint stores it today; nothing compares against a pre-SharePoint original. Migmate never requests conversion, so Drive receives an ordinary blob. The live `checksum_fresh_upload` probe used random `.bin` bytes only: no Office, PDF, or HTML file has been round-tripped live.
- **A listed size that disagrees with the downloaded bytes blocks execution.** Both `stageSource` and `verifyItem` treat `source.size !== downloaded bytes` as `FileSourceChangedError`, which is `retryable` and `transient`. When the disagreement is persistent (rclone's documented Live Photos case; plausibly download-time IRM), the unit exhausts its retry budget and `execute` ends `blocked` with no finding for the item. Reproduced with `FakeFileMigrationPort` (one file listed at 999 bytes serving 11): outcome `blocked`, state `blocked`, the file absent from execute rows and from the destination, its healthy sibling copied. Rerunning `execute` repeats it; excluding the item and replanning is the only way through today. [rclone inconsistent sizes](https://rclone.org/onedrive/#unexpected-file-sizehash-differences-on-sharepoint), [Live Photos size difference](https://rclone.org/onedrive/#live-photos-uploaded-from-ios-small-video-clips-in-heic-files)
- **Microsoft calls the upload-time size change intended.** On the upload-size bug report (PDF, Office, and HTML files report a different size after a session upload to a SharePoint library; plain text and OneDrive for Business do not), Microsoft replied: "This is a feature in SharePoint document libraries that has been around for some time."
